## Findings

### Critical

#### A2 SIZE changes can still put model replacement work on the audio callback
Evidence: `src/NAMControl.cpp:574-580` creates an enabled slimmable size slider, and `src/NAMControl.cpp:2145-2147` calls `NAMProcessor::setSlimmableSize()` on slider changes. `src/NAMProcessor.cpp:253-259` stores the value and immediately forwards it to `namCore->setSlimmableSize()` when the current model is slimmable. `src/NAMCoreA2.cpp:120-132` calls upstream `SetSlimmableSize()`.

The important part is upstream behavior. `external/NeuralAmpModelerCoreA2/NAM/slimmable.h:16-21` explicitly says `SetSlimmableSize()` is thread-safe but not real-time safe. In the WaveNet slimmable implementation, `SetSlimmableSize()` stages a rebuilt model (`external/NeuralAmpModelerCoreA2/NAM/wavenet/slimmable.cpp:445-452`), and the next audio `process()` installs it (`external/NeuralAmpModelerCoreA2/NAM/wavenet/slimmable.cpp:455-463`) by replacing `_active_model` and `_current_channels`. That path can release the old model/shared ownership and replace vector storage on the audio callback.

This contradicts the sprint's RT intent. The guard in `tests/rt_hosting_sprint_test.cpp:294-300` only proves the literal text `SetSlimmableSize` is absent from `NAMProcessor::processBlock`; it does not prove that a slider change cannot cause upstream model replacement during the next `process()`.

Impact: moving the SIZE slider while audio is active can still cause audio-thread model swap/release work, risking dropouts or callback overruns.

Recommended fix: make SIZE a deferred heavy state change. Store the requested value atomically, but apply it only when the processor is inactive or during an explicitly non-audio transition. Until that exists, disable/hide the slider while prepared or mark it pending and apply on stop/reload. Add a regression test that fails if prepared/live `setSlimmableSize()` forwards to the core.

### Important

#### A2 routing rejects real NAM 0.5.x files that do not carry `architecture_version`
Evidence: `src/NAMCore.cpp:56-64` classifies A2 only when top-level `architecture_version == 2`. `src/NAMCore.cpp:108-120` sends everything else to the legacy `nam::get_dsp()` path. The vendored A2 core supports file versions `0.5.0` through `0.7.0` (`external/NeuralAmpModelerCoreA2/NAM/get_dsp.h:65-66`) and its parser constructs models from `version`, `architecture`, `config`, `weights`, and sample-rate metadata (`external/NeuralAmpModelerCoreA2/NAM/get_dsp.cpp:172-186`), not from `architecture_version`.

The fixture policy document records that the official NAM Plugin `v0.7.15` sample `REAPER/model.nam` is file version `0.5.2` and has no `architecture_version` field (`tests/fixtures/nam/README.md:7-14`; `docs/superpowers/plans/2026-06-19-nam-a2-migration.md:265-274`). The audit conclusion in that doc says this exact file "does not exercise Pedalboard's explicit A2 route"; adversarially, that is the bug. A NAM file new enough for the A2-capable core but missing `architecture_version` will be sent to the old 0.1.x core and likely fail.

Impact: real A2-era `.nam` files from official sources can fail to load even though the A2 core is present.

Recommended fix: route based on NAM file version/support floor as well as `architecture_version`, or attempt legacy first and fall back to A2 only for unsupported-version/unsupported-architecture failures without replacing the current model on failure. Add an exact runtime fixture or generated fixture for a `0.5.x` unmarked file.

#### A2 sample-rate rejection can leave `NAMProcessor` claiming a model is loaded after the core cleared it
Evidence: `NAMCoreA2::prepare()` clears its model when host and model sample rates do not match (`src/NAMCoreA2.cpp:140-151`). `NAMCore::prepare()` notices that and clears only its internal `impl->modelLoaded` (`src/NAMCore.cpp:204-208`). `NAMProcessor::prepareToPlay()` calls `namCore->prepare()` (`src/NAMProcessor.cpp:94-95`) but never synchronizes `NAMProcessor::modelLoaded` or `currentModelFile`. Public state still comes from `NAMProcessor::isModelLoaded()` (`src/NAMProcessor.h:64-70`) and `NAMProcessor::getModelName()` (`src/NAMProcessor.cpp:239-245`).

This can happen when an A2 model is loaded or restored before `prepareToPlay()`, because `NAMCore::loadModel()` passes `impl->prepared` as the sample-rate enforcement flag (`src/NAMCore.cpp:108-112`). If not prepared, the model can be accepted first and then cleared during prepare once the real host sample rate is known.

Impact: UI/state can report a model as loaded while `NAMCore` is silently passing through. That is especially bad for patch restore: a user may think the saved NAM model is active when it has been dropped.

Recommended fix: after `namCore->prepare()`, if `!namCore->isModelLoaded()`, clear `NAMProcessor::modelLoaded` and `currentModelFile` or surface a load error. Prefer enforcing sample-rate before accepting a model when the intended host rate is known.

#### The current tests mostly prove source shape, not NAM runtime behavior
Evidence: `tests/CMakeLists.txt` does not compile `src/NAMCore.cpp` or `src/NAMCoreA2.cpp`; this is also asserted by the new fixture-gap test itself (`tests/nam_processor_test.cpp:1747-1763`). The A2 routing, failed-load, and state-restore tests read source text and search for substrings (`tests/nam_processor_test.cpp:1688-1839`; `tests/rt_hosting_sprint_test.cpp:281-338`).

The fresh test runs are real and green: `[nam]` passed 436 assertions in 45 cases, `[rt][nam]` passed 57 assertions in 3 cases, and full CTest passed 267/267. But those results do not exercise actual A2 model loading, sample-rate rejection, slimmable model changes while prepared, or fallback routing from old core to A2 core.

Impact: the branch can pass every current test while still failing the real A2 load path and still violating the RT intent via slimmable model swap.

Recommended fix: wire a focused runtime NAM test target or adapter-level test that compiles `NAMCoreA2` and loads exact fixtures. If fixtures cannot be committed, add a manual verification harness that runs against a user-supplied model path and records model metadata/hash in the audit output.

4. The final status "legacy path preserved" is true in the narrow sense that the legacy `ResamplingNAM` path still exists (`src/NAMCore.cpp:120-132`). It is not enough to prove no legacy regressions because no runtime legacy fixture is exercised.
